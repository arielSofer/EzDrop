# סביבת פיתוח ולמידה מונחית בדפדפן: מאפס לאפליקציית Android מלאה

מסמך מתודולוגיה ואפיון מוצע. היכולות המתוארות כאן הן דרישות לפיתוח, ולא הצהרה שהן כבר ממומשות.

תוכנית העבודה המפורטת נמצאת ב[תוכנית פיתוח סוכן הלמידה בעברית](hebrew-learning-agent-implementation-plan.he.md), כולל חוויית הסוכן בצד שמאל, אלגוריתם המשימות, מדיניות עלויות ושלבי המימוש.

## 1. ההבטחה לתלמיד

התלמיד בונה בעצמו אפליקציה אמיתית ב־Kotlin וב־Jetpack Compose, בתוך התוכנה שלנו בדפדפן. המלווה מסייע לו לאפיין, לעצב, לכתוב, להריץ, לבדוק ולתקן — עד שיוכל להסביר את עבודתו ולפתח יכולת חדשה באופן עצמאי.

**סדר העבודה המחייב: תחילה מעצבים את מסכי האפליקציה בעורך העיצוב הקיים בתוכנה; לאחר מכן לומדים לכתוב את הקוד שמממש אותם; בהמשך מחברים את הלוגיקה, הנתונים ויכולות המכשיר.** העיצוב שהתלמיד יוצר הוא הבסיס האישי לשיעורים ולמשימות הקוד שלו.

הלמידה כוללת את כל שכבות המוצר: מבנה הפרויקט, עיצוב, ניווט, ניהול מצב, לוגיקה עסקית, הרשמה והתחברות, נתונים מקומיים ושרת, חומרת המכשיר, בדיקות והפקת גרסה להתקנה. כל יכולת נלמדת כחלק מפרויקט מתפתח, עם תוצאה שאפשר לראות ולהפעיל.

״מאפס״ פירושו שאין הנחת ידע מוקדם סמויה. לומדים גם מהו קובץ, היכן כותבים, מהו import, מהי תלות ומה משמעות שגיאת בנייה. ספריות ושירותים קיימים נלמדים ומשולבים; אין צורך להמציא מחדש מערכת הצפנה או ספריית ממשק כדי להבין כיצד להשתמש בהן.

## 2. סביבת העבודה בתוך הדפדפן

בכניסה ראשונה למסלול התלמיד מגיע למסך **Design הקיים**, עם הקנבס, כלי העיצוב, השכבות ומאפייני הרכיבים. המלווה מציג סיור קצר בתוך המסך ומנחה אותו ליצור את מסכי האפליקציה שלו. שלב זה אינו דורש כתיבת קוד או הגדרת סביבת Android.

לאחר שהתלמיד הכין את מסכי המסלול, פעולה בשם **״מתחילים לכתוב את המסכים שלי״** פותחת את הלמידה בקוד באותו פרויקט. מופיעים העיצוב ששמר, עורך הקוד ומשימת המימוש הראשונה. בחזרה למערכת ממשיכים מהשלב האחרון, עם אפשרות לחזור לעיצוב בכל עת.

לסביבת הלמידה תהיה משימה פעילה אחת, עם אפשרות לפתוח כל חלק בפרויקט:

| אזור | מה התלמיד עושה בו |
| --- | --- |
| מפת הפרויקט | רואה את המסכים, היכולות, התלויות וההתקדמות שלו |
| כרטיס משימה | מקבל יעד קטן, הסבר לצורך בו ותנאי הצלחה גלויים |
| עץ קבצים ועורך קוד | יוצר ועורך את קובצי הפרויקט האמיתיים, עם שגיאות מקושרות לשורה |
| עורך העיצוב הקיים | יוצר תחילה את מסכי האפליקציה, מסדר רכיבים וקובע צבעים, טיפוגרפיה וריווח |
| העיצוב לצד המימוש | בשלב הקוד רואה את העיצוב ששמר לצד התוצאה של הקוד שכתב ומשווה ביניהם |
| הרצת Android | מפעיל את האפליקציה, לוחץ, מקליד ומבצע תרחישי בדיקה |
| מלווה אישי | מבקש הסבר, רמז, פירוק שורה, ניסוי או סקירת שינוי |
| מעבדת נתונים ומכשיר | מדמה תגובות שרת, הרשאות, ניתוק רשת ונתוני חיישנים |
| בדיקות ויומן ריצה | רואה מה רץ בפועל, מה נכשל ואיזה מידע תומך במשוב |

ההסברים בעברית וב־RTL. הקוד, הנתיבים והלוגים ב־LTR. הנתונים נשמרים כך שרענון הדף מאפשר להמשיך מאותה משימה עם הקוד והמשוב הקודמים.

לחיצה על שורה תציע: **הסבר לי**, **למה היא כאן**, **מה יקרה אם אשנה**, **הראה את זרימת הנתונים**, **תן לי תרגיל דומה**. המלווה מתייחס לגרסה הנוכחית של הקובץ ולמיקום המדויק של הבחירה.

## 3. מחזור הלמידה: מעיצוב המסכים למימוש ולהבנה

תחילה התלמיד מעצב בקנבס הקיים את מסכי המסלול ומגדיר מה אמור לקרות בכל אחד. המלווה מסייע לו לבדוק את היררכיית הרכיבים ואת מצבי המסך. התלמיד בוחר להתחיל בקוד, והמערכת שומרת גרסת עיצוב כיעד למימוש ובונה ממנה רצף משימות.

לאחר המעבר לקוד, כל משימה מתבצעת במחזור קצר ומתייחסת לרכיב או להתנהגות מתוך העיצוב שלו:

1. **מבינים צורך:** ״המשתמש צריך לדעת שההרשמה בתהליך ולא ללחוץ שוב.״
2. **מנבאים:** ״איזה מצב נצטרך להחזיק, ואילו רכיבים ישתנו בזמן ההמתנה?״
3. **כותבים:** התלמיד מממש חלק קטן מהעיצוב או מההתנהגות שלו, בדרך כלל 5–10 שורות או יחידה רעיונית אחת.
4. **מריצים ומשווים:** בונים ומפעילים את הקוד ומשווים לעיצוב ששמר ולתוצאה הצפויה, או מריצים בדיקה מתאימה לשלב.
5. **מסבירים:** התלמיד מתאר מה קרה ומקשר בין האירוע, המצב והממשק.
6. **משנים תנאי:** מנסים רשת איטית, תשובה שגויה, לחיצה נוספת או חזרה למסך.
7. **מעבירים ידע:** התלמיד מיישם את אותו עיקרון בתרחיש חדש עם פחות עזרה.

אין מגבלת שורות קשיחה: לא מפרקים ביטוי באופן שמסתיר את משמעותו. חזרה על תחביר שכבר הובן מתקצרת; מושג חדש או טעות חוזרת מקבלים יותר מקום.

## 4. פירוק מדויק של כל שורת קוד

לכל שורה חדשה או משמעותית נבדקות שש שאלות:

| שאלה | מטרת ההסבר |
| --- | --- |
| מה היא עושה? | תרגום לפעולה פשוטה ולתוצאה נצפית |
| מה משמעות כל חלק? | מילת מפתח, שם, טיפוס, אופרטור, פרמטר וערך חזרה |
| למה היא נמצאת כאן? | קשר לדרישה ולחלוקת האחריות בין הקבצים |
| מה קורה בזמן ריצה? | יצירה או קריאה של ערכים, בעלות, מחזור חיים, השהיה ועדכון UI לפי הרלוונטיות |
| מה יקרה אם נשנה אותה? | ניבוי לפני הניסוי והבחנה בין שגיאת קומפילציה לשגיאת התנהגות |
| איך נוכיח שהבנו? | שינוי עצמאי, בדיקה או הסבר על מקרה חדש |

אין להמציא הסבר זיכרון לכל שורה. המלווה מבדיל בין משמעות השפה לבין פרטי המימוש של הקומפיילר וסביבת הריצה. תרשים מושגי מסומן כהמחשה, ונתון שנמדד מסומן כמדידה.

### דוגמה מתוקנת: מצב מסך ב־Compose

בתוך פונקציית Composable, כאשר `viewModel.uiState` הוא `StateFlow<WorkoutUiState>`:

```kotlin
import androidx.compose.runtime.getValue
import androidx.lifecycle.compose.collectAsStateWithLifecycle

val state by viewModel.uiState.collectAsStateWithLifecycle()
```

הדוגמה מניחה שתלות Lifecycle Compose הוגדרה בפרויקט. במסגרת השיעור התלמיד מוסיף גם את התלות וה־imports, ומבין את תפקידם.

| חלק | ההסבר לתלמיד |
| --- | --- |
| `val` | מאפיין מקומי לקריאה בלבד. לא ניתן להציב בו באמצעות `state = ...`. אין פירושו שהערך שנקרא ממאפיין מואצל לעולם לא ישתנה, ואין בו הבטחה להקצאת ״מצביע קבוע על ה־Stack״. |
| `state` | השם שבחרנו לערך מצב המסך שאליו ניגשים דרך ההאצלה. |
| `by` | מעביר את הקריאה למנגנון ההאצלה. כאן נעשה שימוש ב־`getValue` של Compose כדי לקרוא את ערך ה־`State`. |
| `viewModel.uiState` | זרם המצב שנחשף ב־ViewModel. אורך חייו תלוי בבעלים של ה־ViewModel; הוא יכול לשרוד שינוי תצורה, אך אינו אחסון קבוע לאחר סיום התהליך. |
| `collectAsStateWithLifecycle()` | אוסף את הזרם בהתאם למחזור החיים ומציגו כ־Compose `State`. קריאות למצב במהלך Composition מאפשרות לתשתית זמן הריצה לתזמן הרכבה מחדש של תחומי הקריאה הרלוונטיים כאשר המצב משתנה. |

ב־Android זהו ממשק האיסוף המומלץ למצב Flow ב־Compose. הרכבה מחדש היא הערכה מחודשת של קוד Composable; אין פירושה בהכרח ציור מחדש של המסך כולו. מקורות: [State and Jetpack Compose](https://developer.android.com/develop/ui/compose/state), [האצלת מאפיינים ב־Kotlin](https://kotlinlang.org/docs/delegated-properties.html), [מחזור החיים של ViewModel](https://developer.android.com/topic/libraries/architecture/viewmodel).

**ניסוי:** מחליפים `by` ב־`=`. ההצהרה עצמה עדיין תקינה; הטיפוס המוסק נעשה `State<WorkoutUiState>`. גישה כמו `state.distanceKm` אינה מתאימה כעת, ויש לקרוא `state.value.distanceKm`. התלמיד מסביר גם מדוע `val` אינו מונע עדכונים דרך ה־delegate.

## 5. מנגנוני ההוראה והעזרה

### הסבר במילים של התלמיד

המלווה בודק קשר סיבתי, ולא התאמה לנוסח או הופעת מילות מפתח. תשובה כמו ״זה אסינכרוני״ דורשת הבהרה: מה ממתין, האם ה־Thread פנוי, ומה מפסיק את העבודה כאשר המסך מסתיים?

אפשר להסביר במשפטים, לעקוב אחר ערכים או לבצע שינוי קוד. קושי בניסוח אינו לבדו הוכחה לחוסר הבנה.

### סולם רמזים

1. שאלה שמכוונת לתופעה.
2. הפניה למושג או למיקום בקוד.
3. פסאודו־קוד או דוגמה אחרת.
4. השלמה חלקית.
5. פתרון מלא לפי בקשה, ואחריו משימת העברה עצמאית.

המלווה אינו משנה קובצי תלמיד בשקט. כאשר הוא מציע קוד, מוצג ההבדל לפני החלתו ונשמרת נקודת שחזור. קבלת פתרון מאפשרת להמשיך ללמוד; היא מסומנת כ״בוצע בעזרה״ ולא כשליטה עצמאית.

### הקוד החבול

מזריקים תקלה אחת בכל פעם לעותק שניתן לשחזר. התלמיד מנבא, מפעיל, אוסף ראיות ומתקן.

- משתנה רגיל שמחזיק מונה ואינו נצפה כמצב Compose: בודקים מדוע שינויו כשלעצמו אינו מבקש עדכון UI.
- השהיה חוסמת על Main: בודקים השפעה על תגובתיות ומבדילים בינה לבין השהיית Coroutine.
- כפתור הרשמה ללא הגנה מפני לחיצה כפולה: בודקים כמה בקשות נשלחו.
- Listener לחיישן שלא הופסק: בודקים אם אירועים ממשיכים להגיע לאחר יציאה מהמסך.
- גישה לנתוני משתמש אחר בסביבת בדיקה: בודקים שהשרת דוחה אותה גם אם ה־UI מסתיר את הפעולה.

`Thread.sleep` חוסם את ה־Thread שבו הוא מופעל; פגיעה ישירה בתגובתיות הממשק תלויה בכך שהוא מופעל על Main ובמשך החסימה. אין לכנות את התרגיל ״זליגת זיכרון״ ללא ראיה לזליגה. `delay` משהה Coroutine בלי לחסום Thread; `suspend` לבדו אינו מעביר עבודה ל־Thread רקע. מקור: [תיעוד delay](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/delay.html).

### מבחן הבנה והמשך למידה

לכל יכולת נשמרים בנפרד: **רץ בהצלחה**, **הוסבר**, **נפתר בעזרה**, **יושם עצמאית**. התקדמות במסלול מונחה דורשת ראיות למושג שעליו תלויה המשימה הבאה. כישלון מוביל לתרגיל ממוקד או להסבר חלופי; עיון בחומר נשאר פתוח. תלמיד מנוסה יכול להוכיח שליטה בתרגיל קצר ולדלג על חזרות.

## 6. המסלול המלא: כל שכבות האפליקציה

הדוגמה המלווה היא אפליקציית פעילות גופנית. אפשר לבחור מוצר אחר ולבנות לו מסלול לפי אותן תלויות.

| שלב | מה התלמיד בונה וכותב | מה מוכיח שהשלב הושלם |
| --- | --- | --- |
| 1. רעיון ואפיון | משתמשים, פעולות, מסכים ומקרי כשל | יודע לתאר מסלול משתמש ולנסח תוצאה רצויה |
| 2. היכרות עם עורך העיצוב הקיים | קנבס, מסכים, רכיבים, שכבות ולוח מאפיינים | יוצר מסך ומוסיף ועורך בו רכיבים בעצמו |
| 3. עיצוב מסכי האפליקציה | צבעים, טקסטים, מרווחים, רכיבים חוזרים ומצבי מסך | מסכי המסלול מעוצבים ושמורים, והתלמיד מסביר את תפקידיהם |
| 4. מעבר מהעיצוב לקוד | בחירת מסך ראשון ופירוקו למשימות מימוש | רואה את העיצוב שלו לצד משימות הנגזרות מהרכיבים שבו |
| 5. פרויקט Android ויסודות Kotlin | מבנה תיקיות, Gradle, Manifest, טיפוסים, משתנים ופונקציות לפי צורכי המשימה | בונה ומריץ את החלק הראשון במסך שלו ומבין את הקוד שכתב |
| 6. מימוש העיצוב ב־Compose | `Row`, `Column`, `Box`, `Modifier`, שדות, כפתורים ורשימות | משחזר בקוד את העיצוב ומתאים אותו לגדלים שונים, RTL ומקלדת |
| 7. אינטראקציה וניווט | אירועים, מצב, מעבר מסכים וכפתור חזרה | שינוי קלט משנה מצב ותצוגה באופן צפוי |
| 8. מבנה הלוגיקה | ViewModel, Coroutines, Flow ו־Repository כשנדרש | יודע לעקוב מהאירוע דרך הלוגיקה אל ה־UI |
| 9. הרשמה והתחברות | אימות קלט, שירות אימות, Session ופרופיל במסכים שעיצב ומימש | מצליח ונכשל באופן צפוי בתרחישי אימות מוגדרים |
| 10. נתונים מקומיים | שמירת העדפות והיסטוריה, מודל נתונים ומיגרציה בסיסית | סוגר ופותח את האפליקציה בלי לאבד נתונים שנועדו להישמר |
| 11. שרת ו־API | בקשות, תשובות, שגיאות, הרשאות וסנכרון | מציג טעינה, הצלחה, ריק וכשל; מונע גישה לא מורשית |
| 12. יכולת המוצר | התחלת אימון, השהיה, סיום, חישובים והיסטוריה | רצף פעולות מלא עובד, כולל לחיצות חוזרות וחזרה למסך |
| 13. חומרה והרשאות | מיקום, חיישנים או מדיה לפי המוצר | מטפל בהיעדר חומרה, סירוב הרשאה והפסקת האזנה |
| 14. איכות | בדיקות יחידה, אינטגרציה ו־UI, נגישות וביצועים | מתקן תקלה לפי ראיות ומציג בדיקה שמזהה אותה |
| 15. גרסה להתקנה | הגדרות סביבה, גרסה, בניית תוצר וייצוא מקור | מתקין ומריץ גרסה בנויה ובודק מסלול משתמש מלא |

כל מושג נלמד בזמן שהוא פותר צורך. אין צורך להציג ארכיטקטורה מורכבת לפני שהתלמיד מבין פונקציה ומצב פשוטים. ״כל האפליקציה״ מוגדר לפי היכולות שנבחרו לפרויקט, עם הרחבות בהמשך.

## 7. קודם מעצבים בעורך הקיים, ואז כותבים את קוד המסכים

### שלב א׳: עיצוב חזותי בליווי המורה

התלמיד עובד במסך העיצוב הקיים של התוכנה. המלווה מסביר היכן יוצרים מסך, כיצד מוסיפים ומסדרים רכיבים וכיצד משנים את המאפיינים שלהם. הוא מלווה אותו בעיצוב המסכים שנבחרו לאפליקציה: למשל פתיחה, הרשמה, התחברות, מסך ראשי ופרופיל.

בשלב זה לומדים היררכיה חזותית, ריווח, צבעים, טקסטים ומצבי רכיב דרך העיצוב עצמו. לדוגמה: התלמיד ממקם כותרת, שני שדות וכפתור הרשמה ומכין גם מראה לטעינה ולשגיאה. הוא מתאר לאיזה מסך אמורה להוביל הצלחה; את הניווט בפועל יממש בשלב הקוד.

### שלב ב׳: הפיכת העיצוב האישי למסלול כתיבה

לאחר בחירה ב־**״מתחילים לכתוב את המסכים שלי״**, המערכת שומרת גרסת עיצוב ומפיקה תוכנית מימוש המבוססת על המסכים והרכיבים שהתווספו בפועל. לכל משימה מקושרים המסך ורכיבי העיצוב הרלוונטיים. התלמיד רואה את העיצוב שלו גם לפני שקיים לו מימוש בקוד.

המלווה מדריך אותו להקים את פרויקט Android, ואז לפרק את המסך הראשון לחלקים. לדוגמה: ״בעיצוב שלך יש כותרת מעל שני שדות וכפתור. נתחיל במבנה שמסדר אותם מלמעלה למטה; אחר כך נממש כל רכיב.״

המעבר יוצר משימות כתיבה; קוד המסכים אינו מתמלא אוטומטית כפתרון מלא. התלמיד כותב את המימוש בהדרגה, עם הרמזים והסיוע שהוגדרו במסמך.

### שלב ג׳: מימוש והשוואה

בסביבת הקוד מוצגים העיצוב השמור, הקובץ הפעיל ותוצאת ההרצה. התלמיד כותב את מבנה המסך, הטקסטים, הריווח והרכיבים, ובודק כיצד כל שינוי מקרב את המימוש לעיצוב. המלווה מסביר גם התאמות למסכים שונים, לטקסט מוגדל ולמקלדת.

בחירת רכיב בעיצוב פותחת את משימת המימוש שלו. לאחר שקיים מיפוי מאומת לקוד, היא יכולה גם להצביע על מיקומו בקובץ. רכיב שטרם נכתב מסומן ״ממתין למימוש״. בדיקת השלמה משלבת מבנה והתנהגות עם השוואה חזותית; צילום מסך דומה לבדו אינו מוכיח מימוש תקין.

### שלב ד׳: חיבור ההתנהגות

לאחר מימוש העיצוב של המסך, התלמיד מחבר את הפעולות שלו: שינוי קלט, בדיקת שדות, לחיצה, טעינה, בקשת הרשמה וניווט. כל התנהגות מקושרת לרכיב ולמצבי המסך שתכנן. אותו עיקרון ממשיך לנתונים ולחיישנים: קודם מתכננים כיצד היכולת תיראה למשתמש, ואז כותבים את המימוש שלה.

### חזרה לעיצוב במהלך הלמידה

התלמיד יכול לחזור לעורך הקיים ולשנות את המסכים. נשמרים בנפרד עיצוב היעד והקוד שמממש אותו. שינוי עיצוב מציג מה השתנה ומעדכן את משימות המימוש הרלוונטיות, תוך שמירת הקוד שכבר כתב. מסך חדש עובר אותו רצף: עיצוב, כתיבת הממשק וחיבור הלוגיקה.

העיצוב השמור קובע את יעד המראה; הקוד השמור קובע מה רץ. התצוגות מציינות את גרסאות העיצוב והקוד שלהן. אין להבטיח סנכרון דו־כיווני אוטומטי של כל קוד Compose שרירותי; שינויים מתורגמים למשימות ממוקדות ואינם דורסים את עבודת התלמיד.

## 8. הרשמה והתחברות: מסלול שלם

התלמיד יבנה בהדרגה:

1. מימוש בקוד של מסכי ההרשמה וההתחברות שכבר עיצב בעורך הקיים: תוויות, מקלדת מתאימה, הצגת סיסמה ומצבי שדה.
2. מודל מצב ואירועים: הקלדה, שליחה, טעינה, הצלחה וכשל.
3. אימות קלט מקומי ומשוב שימושי; הבחנה בינו לבין אימות שמבצע השירות.
4. ממשק שירות, מימוש מדומה ובהמשך ספק אימות בסביבת פיתוח.
5. טיפול בבקשה איטית, ניסיון כפול, פרטי כניסה שגויים וכשל רשת.
6. אימות דוא״ל ואיפוס סיסמה, לפי ספק האימות שנבחר.
7. שחזור Session, יציאה מהחשבון וניווט לאחר פתיחת האפליקציה מחדש.
8. פרופיל משתמש ונתונים המשויכים למזהה שלו.
9. הרשאות בצד השרת: משתמש אחד אינו יכול לקרוא או לשנות נתונים פרטיים של אחר.
10. בדיקת התהליך כולו, כולל הצלחת אימות לצד כשל ביצירת פרופיל ואפשרות התאוששות.

לכל צעד יש תחילה חוזה התנהגות ברור ולאחריו קוד ובדיקה. אין לשמור סיסמאות גולמיות במסד נתונים, בלוגים או בהקשר שנשלח למלווה. מפתחות שרת נשארים בשירות השרת.

אפשר לתרגל מול Firebase Authentication Emulator בסביבת לימוד ייעודית; הממשק יסמן בבירור אם התרחיש מדומה או מול שירות מוגדר. מקור: [Firebase Authentication Emulator](https://firebase.google.com/docs/emulator-suite/connect_auth).

## 9. מעבדת חומרה וחיישנים

התלמיד בוחר יכולת מתוך מפת המוצר, והמערכת מציגה את תנאי השימוש והבדיקה שלה:

| יכולת | מה לומדים | תרחישים לתרגול |
| --- | --- | --- |
| מיקום/GPS | בקשת הרשאה, דיוק, עדכונים, חישוב מרחק והפסקת מעקב | מסלול מוקלט, מיקום משוער, קפיצה שגויה, היעדר מיקום וסירוב |
| מד תאוצה | צירי X/Y/Z, יחידות, קצב דגימה וסינון בסיסי | נייח, תנועה, סיבוב ורעש |
| ג׳יירוסקופ | מהירות זוויתית ופרשנות הנתונים | סיבובים מוקלטים והיעדר חיישן |
| מונה צעדים | זמינות, משמעות הערך והמרה לתוצאת אימון | התחלה מערך שאינו אפס ונתונים חסרים |
| מצלמה | פתיחה, צילום, תוצאה, ביטול ושמירה | תמונת בדיקה, ביטול והיעדר גישה |
| מיקרופון | הקלטה, מחזור חיים וניהול קובץ | התחלה, עצירה, הפרעה וסירוב |
| Bluetooth | גילוי, חיבור, קריאה וניתוק לפי התקן | התקן מדומה, כשל חיבור ואיבוד קשר |

מצלמה, מיקרופון ו־Bluetooth נלמדים כיכולות מכשיר לצד חיישנים; הם אינם כולם חלק מאותו Sensor API.

לכל יכולת חוזר אותו תהליך: **הצורך → זמינות ותמיכה → הרשאה נדרשת → התחלת שימוש → פירוש נתונים → עדכון מצב → הצגה → הפסקה וניקוי → בדיקה**. דרישות ההרשאות נבדקות לפי ה־API וגרסת Android של הפרויקט; אין להניח שלכל חיישן נדרשת אותה הרשאה.

המעבדה תתמוך בהזרקת סדרת אירועים עם חותמות זמן, עצירה, שינוי קצב ושחזור אותו ניסוי. אם מותקן אמולטור Android מתאים, אפשר להשתמש גם בבקרי החיישנים הווירטואליים שלו. מקור: [Android Sensors Overview](https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview).

שלוש רמות ראיה נפרדות יוצגו לתלמיד: **נבדק עם נתונים מדומים**, **נבדק באמולטור**, **נבדק במכשיר פיזי**. יכולת שעברה סימולציה אינה מוצגת כמאומתת בחומרה אמיתית.

## 13. דיוקים נוספים למתודולוגיה המקורית

- `StateFlow` כשלעצמו אינו מפעיל Recomposition; צריך חיבור למצב שנצפה ב־Compose. קיימים גם מקורות נתונים אחרים עם חיבור מתאים.
- `data class` אינה בהכרח Immutable. הדבר תלוי במאפיינים ובאובייקטים שבתוכה; `copy` יוצר עותק רדוד. מקור: [Data classes](https://kotlinlang.org/docs/data-classes.html).
- יצירת אובייקט חדש אינה לבדה ערובה לפליטה מ־StateFlow: השוואת הערכים מבוססת על `equals`. `copy` עם אותם ערכים עשוי שלא להוביל לפליטה חדשה. מקור: [StateFlow](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/-state-flow/).
- `sealed interface` מתאים לאירועים מסוגים שונים עם מטען שונה לכל מופע. גם `enum` יכול לכלול מאפיינים; ההבדל הוא מערכת מופעים קבועה לעומת היררכיה סגורה עם מופעי אירוע ונתונים משתנים. מקורות: [Sealed classes and interfaces](https://kotlinlang.org/docs/sealed-classes.html), [Enum classes](https://kotlinlang.org/docs/enum-classes.html).

הליווי הלימודי מתחיל בתוך מצב **Design הקיים**: סיור בכלים, משימות עיצוב ועזרה לפי המסך והרכיב שנבחרו. פעולת **״מתחילים לכתוב את המסכים שלי״** מעבירה לסביבת המימוש המונחה באותו פרויקט ומשמרת את עיצוב התלמיד כנקודת ייחוס. נדרשות הרחבות ייעודיות לפרויקט Android, שמירת עבודת תלמיד וגרסאות עיצוב, יצירת משימות מהעיצוב, מנוע הדרכה והערכה, בנייה והרצה של Kotlin ומעבדת תרחישים. עורך הקוד הקיים יכול לשמש בסיס לחוויית העריכה; מסלול ההרצה הנוכחי אינו מסלול Android.

סדר מימוש מוצע, כאשר כל שלב מוסיף יכולת עובדת:

1. **פרוסה מלאה קטנה:** כניסה לעורך Design הקיים, עיצוב ושמירת מסך, מעבר מפורש למשימות המבוססות עליו, כתיבת המימוש שלו ב־Compose והרצתו באמולטור בדפדפן לצד עיצוב היעד; משימת הבנה אחת עם ראיות.
2. **מספר מסכים ואינטראקציה:** עיצוב מסכי המסלול, מימוש טופס, מצב, ניווט ושגיאות; חזרה לעיצוב ועדכון משימות בלי אובדן עבודת תלמיד.
3. **אימות ונתונים:** הרשמה והתחברות בסביבת תרגול, פרופיל, Session ובדיקת בידוד משתמשים.
4. **לוגיקת מוצר וחיישן ראשון:** תרחיש פעילות מקצה לקצה ונתונים ניתנים לשחזור, עם אימות פיזי נפרד לפי הצורך.
5. **הרחבת המסלול:** יותר יכולות מכשיר, פרויקטים, מדדי שליטה, כלי מורה וייצוא תוצר מלא.

## 15. הוראות יסוד למלווה

> אתה מלווה אישי לפיתוח Android בתוך סביבת הלמידה בדפדפן. עזור לתלמיד לבנות את הפרויקט בעצמו ולהבין את החלטותיו.
>
> התחל בעורך העיצוב הקיים. הכר לתלמיד את הכלים ולווה אותו בעיצוב מסכי האפליקציה לפני תחילת הקוד. לאחר המעבר לכתיבה, בנה את המשימות מתוך העיצוב ששמר והצג אותו לצד המימוש. אל תמלא את קוד המסכים אוטומטית במעבר זה.
>
> לפני כל משימה בדוק את השלב הפעיל, העיצוב, הקוד הנוכחי אם קיים, התוצאה האחרונה והידע המקדים. הצג יעד שימושי קטן ושאלת ניבוי. בשלב העיצוב הנחה לפעולה בעורך החזותי; בשלב הקוד בקש מהתלמיד לכתוב יחידה אחת ובדוק אותה בכלים המתאימים.
>
> הסבר תחביר, אחריות והתנהגות בזמן ריצה לפי רמת התלמיד. השתמש בניסוי כאשר הוא מבהיר את הסיבה. קשר כל שאלה לקוד ולמשימה הנוכחיים.
>
> תן רמזים בהדרגה. הצג פתרון מלא כאשר התלמיד מבקש אותו, סמן את העזרה וחזור לתרגול עצמאי בהמשך. אל תדרוס עבודת תלמיד.
>
> הפרד בין תוצאה שנמדדה לבין השערה, בין סימולציה לבין מכשיר אמיתי ובין קוד שעבר בדיקה לבין הבנה שהוכחה. לעולם אל תדווח שהרצת דבר שלא הורץ.
>
> למד את כל שכבות היכולת: עיצוב, קוד, מצב, שרת או חומרה, שגיאות ובדיקות. סיים כל יכולת בתרחיש שימוש עובד ובמשימת העברה עצמאית.

## 16. תנאי הקבלה לחזון

בכניסה הראשונה התלמיד רואה את עורך העיצוב הקיים ויכול לעצב ולשמור את מסכי המסלול לפני כתיבת קוד. המעבר לכתיבה מציג את המסכים שעיצב ומייצר משימות מימוש המקושרות אליהם. אפשר לחזור לעיצוב ולעדכן את היעד תוך שמירה על הקוד שנכתב; רענון משחזר גם את שלב העבודה וגם את הגרסאות השמורות.

מתוך העיצובים שלו התלמיד כותב מסכים ולוגיקה, מפעיל הרשמה והתחברות, שומר נתונים ומשלב יכולת מכשיר שנבחרה למסלול. הוא מקבל אבחון המבוסס על העיצוב והקוד שלו, מפעיל בדיקות וממשיך מאותה נקודה לאחר חזרה למערכת.

הוא יכול לייצא את מקור הפרויקט ולהפיק תוצר Android להתקנה. ליד כל יכולת מופיע היכן נבדקה. שליטה בלמידה נרשמת לאחר הסבר ויישום עצמאי, ולא רק לאחר יצירת קוד או לחיצה על כפתור ״המשך״.
